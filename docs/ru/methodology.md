# Методика CCSDD — Committee Cycle Spec-Driven Development

[English version → ../en/methodology.md](../en/methodology.md)

## Имя

**CCSDD** — *Committee Cycle Spec-Driven Development*:
спек-ориентированная методика, организованная как **цикл комитетов** —
архитектурный комитет проектирует, исполнительный комитет строит,
ревьюверы не входят ни в один.

Почему такое имя: оно ставит метод в семью SDD и сразу заявляет оба
отличия — исполнителями спек являются вероятностные LLM-агенты (за
каждым допущением SDD стоит *механический* гейт, а не
промпт-инструкция), и власть разделена между комитетами плюс
ревьюверами вне комитетов (maker–checker), а не сосредоточена в одном
ассистенте.

## Задача, которую решает методика

Классические модели процесса (SDLC, Scrum) и новые spec-driven
инструменты (SDD/Spec Kit, OpenSpec) исходят из того, что исполнитель —
дисциплинированный человек или детерминированный пайплайн. LLM-агент —
ни то ни другое: он может писать отличный код *и* незаметно править
защищённый файл, закрывать свою задачу, «аппрувить» собственную
работу или правдоподобно отчитаться о том, чего не делал.

Поэтому базовая аксиома CCSDD: **любое действие агента — недоверенный
вывод, который обязан пройти детерминированную проверку, прежде чем
станет состоянием**. Всё остальное в методике — следствие этой
аксиомы.

## Наш подход

### 1. Недоверенные акторы + детерминированные гейты

Каждое правило, от которого зависит корректность, существует в двух
видах: текст в спеке/правилах **и** исполняемая проверка. Инстанс
агента не может «решить» пропустить линт, закоммитить защищённый путь или
смержить без вердиктов — соответствующие exec'ы запрещены в политике
(`config/policy.json`), а переходы состояний делают только скрипты
`canon/bin/` (bash + git + gh, детерминированные, fail-closed).
Промпты и профили ролей — описание обязанностей; принуждение — гейты.

### 2. Двухкомитетная структура + ревью вне комитетов

- **Архитектурный комитет** — root-директор (главный инстанс агента в
  репозитории) + партнёры-консультанты (architect-partner,
  product-partner — канонические роли, привязанные к топ-моделям) +
  человек-арбитр. Проектирует roadmap и дизайн каждого пункта.
  Проектный код не правит.
- **Исполнительный комитет** — исполнитель-субагент (`code_writer`) +
  условный `designer` (спавнится только когда контракт декларирует
  оси `## Delegated decisions`: закрывает каждую ось в impl spec,
  гейт `design_spec_check.sh` до старта исполнителя) +
  консультанты (design-partner, product-partner — рабочий тир).
  Реализует один пункт roadmap в рамках белого списка.
- **Ревьюверы — вне обоих комитетов**: судья, reviewer-субагент,
  резолвер, читатель. Вердикт выносится только по зафиксированным
  артефактам и замороженному контракту; ни один комитет не судит свою
  работу.

Разделение полномочий механическое, не организационное: у исполнителя
нет git в разрешённых exec, у git-агента нет права мержа, а merge-гейт
мержит только по вердиктам ревьюеров, привязанным к текущему
head sha — никогда по слову инстанса.

### 3. Инстанс-директор (event-driven)

Root — один долгоживущий инстанс агента на репозиторий: единственный писатель
плана и статусов, спавнит ролевых субагентов с узкими контекстами
(пакеты по белым спискам — пункт, контракт read-only, срез файлов),
собирает их отчёты и вердикты, ведёт журналы. Узкий контекст субагента
— тоже механизм: он физически не может увидеть лишнее, а его
`request_reference` к директору ограничен срезом `≤N строк ≤M файлов`.

### 4. Контракт как замороженный объект

Каждый пункт roadmap едет на контракте: G/W/T-сценарии, белый список
editable-путей, risk-флаг, команда успеха. Жизненный цикл
`draft → judged → signed_off`: судья проверяет черновик, человек
подписывает, контракт замораживается — в конверт уходит его SHA-256.
Дальше судья проверяет артефакты **против замороженных байтов**, а
непротиворечивость контракта реальности перепроверяется на спавне
пункта (устарел — re-judge или PLAN_DELTA, но не «поправить по ходу»).

### 5. Человек — держатель гейтов, а не наблюдатель

`👨‍💻`-гейты: аппрув roadmap, sign-off каждого контракта (или пакетная
проработка первых N — §2a), решения по эскалациям и PLAN_DELTA,
публикация канона. Сам merge — объективный: APPROVE ревьюеров +
зелёные проверки + `expected_sha` — если только `.changes`-фрагмент
не объявляет `manual_gate: true`, который паркует merge до явного
решения разработчика.
Решение оформляется **конвертом** `{verdict, artifact_sha, sig,
signed_by, ts}` — пишется мимо LLM-контекста, подписывается ключом,
лежащим вне workspace, и проверяется потребителями механически по
хешу артефакта. Для удалённого человека (ноутбук без агентов,
сессии по SSH) тот же конверт едет одной строкой `CCSDD-SIGNOFF-1|…`,
вставленной в чат агента — чат здесь только транспорт: вставленная
строка остаётся криптографическим конвертом.
«Устный» аппрув невозможен: гейт проверяет конверт,
а не текст в чате.

### 6. Цепочка верификации на пункт

`designer (делегированные оси → impl spec, гейт до исполнителя) →
исполнитель (опрос до кода → код+тесты → зелёный прогон) → судья
(≤3 раундов по замороженному контракту) → git-агент (кандидат с явным
sha + push + открытие PR) → reviewer-субагент (отдельная
учётка, читает только удалённое хранилище, APPROVE привязан к head
sha, директор его вердикт не
фильтрует) → гигиена (diff-скан,
атрибуция, `.changes`-фрагмент) → merge-гейт (перепроверка в
изолированном worktree + `expected_sha` + APPROVE каждого ожидаемого
ревьюера на текущем head + зелёные обязательные проверки) →
Release-on-Merge (версия из `.changes/`).`

Для `risk: high` — вердикты двух независимых семейств моделей плюс
подтверждение человека до сборки PR.

### 7. Ограниченные петли и лестница эскалации

Доработки ограничены: >3 раундов спора с судьёй/ревьювером → резолвер
→ стоп пункта, а не вечный треш. Неоднозначность идёт вверх по
лестнице: вопрос → комитет уровня → архкомитет → человек (терминал);
обход уровня запрещён. Обязательный **опрос до кода**: исполнитель
фиксирует допущения и трактовки критериев до написания кода — пустой
опрос сам по себе сигнал судье.

### 8. Целостность самой методики

Методика — тоже артефакт под контролем: канон деплоится verbatim по
`MANIFEST.json` с sha256-картой (дрифт ловится `check_setup.sh`),
деплоится, а не трекается (gitignore-блок), per-repo **канарейка** в
хвосте `RULES.md` доказывает, что правила инстанса не обрезаны.
Изменение канона — single-writer через `canon_pub.sh` с подписанным
конвертом человека; самоизменение канона агент-инстансом запрещено.
Реестр акторов (`actors.json` + capability-токены) отделяет
полномочия ролей: операцию `close` удостоверяет токен, а не
должность в тексте.

## Базовые примитивы

| Примитив | Что это |
|---|---|
| **Пункт roadmap** | Единица работы; автономная задача с артефактом на выходе. |
| **Контракт** | Спека приёмки пункта (G/W/T, белый список, risk-флаг). `draft → judged → signed_off`, заморозка по SHA-256. |
| **Конверт решения** | Решение человека, привязанное к хешу артефакта — пишется мимо LLM-контекста. |
| **Гейт** | Детерминированный скрипт: `check_setup`, `verify_constraints`, `hygiene_check`, `repo_merge`, `canon_pub`. |
| **Журнал вердиктов** | `cycle_log`, `harness_log`, вердикты — аудируемый след цикла. |
| **Канарейка** | Per-repo токен в хвосте `RULES.md`; отсутствие ⇒ правила обрезаны ⇒ halt. |
| **Канон** | Сама методика как версионируемый, хеш-пиннутый, single-writer контент. |

## Карта наследования — что и откуда взято

### Из SDD (Spec-Driven Development: Spec Kit, Kiro и т.п.)

**Взято:** spec-first процесс; критерии приёмки как исполняемые
Given/When/Then-сценарии; ревьюится спека, а не код.

**Изменено:** в SDD человек ревьюит документ — в CCSDD спека
становится *замороженным объектом*: sign-off пишет SHA контракта в
подписанный конверт, судьи проверяют артефакты *против замороженных
байтов*, имплементация по неподписанному контракту не стартует.
Дрейф спеки после sign-off — эскалация `PLAN_DELTA`, а не правка.

### Из OpenSpec

**Взято:** изменение-как-объект (предложение с собственным жизненным
циклом), явная работа с дельтами, версионируемые артефакты изменений —
зеркалится жизненным циклом контракта и фрагментами
`.changes/<slug>.md` (конвенция changesets).

**Изменено:** OpenSpec доверяет ассистенту следовать конвенциям; CCSDD
заменяет конвенцию гейтами — те же идеи принуждаются
`verify_constraints.sh`, `hygiene_check.sh` и merge-гейтом.

### Из SDLC

**Взято:** фазовый каркас — план → дизайн → построение → проверка →
релиз — отображён на жизненный цикл пункта с явными условиями
входа/выхода каждой фазы.

**Изменено:** никаких больших фаз на весь продукт; фазы идут по
*пункту roadmap*. Единственный общепродуктовый гейт — аппрув самого
roadmap.

### Из Agile / Scrum

**Взято:** roadmap ≈ бэклог, пункты ≈ issues, человек ≈ product owner
с решающим словом, метка `backlog` для неприоритизированных идей.

**Отвергнуто:** церемониальный слой (стендапы, спринты, оценочные
ритуалы). Координационные издержки заменены событийными гейтами и
журналом вердиктов — агент не ходит на митинги.

### Из GitOps / IaC

**Взято:** деплой желаемого состояния по манифесту (`MANIFEST.json` +
sha256-карта), канон *деплоится, а не трекается*, фенсинг релизов
тегами `canon-v<version>`, детект дрифта по хешам.

### Из supply-chain security (паттерны SLSA / in-toto / Sigstore)

**Взято:** хеш-пиннинг контента, аттестационные конверты, привязывающие
решение к дайджесту артефакта, per-deploy канарейки, HMAC-подписанные
аппрувы человека с ключом вне workspace.

### Из финансовых контролей (four-eyes / maker–checker)

**Взято:** разделение полномочий как жёсткая граница — писатель не
может коммитить (git отсутствует в exec-разрешениях), коммитящий не
может мержить, мерж требует APPROVE каждого ожидаемого ревьюера,
привязанного к head sha, а ревьюверы стоят *вне обоих комитетов* —
ни один комитет не судит свою работу.

### Из практики code review / branch protection

**Взято:** merge-гейт — это branch protection, сделанный механическим:
перепроверка в detached worktree + наличие вердиктов + свежесть
`expected_sha` + зелёные обязательные проверки, плюс ревьюерская
учётка, которую директор не фильтрует.

## Что сознательно НЕ взято

- **Последовательную жёсткость водопада** — пункты идут инкрементально
  и независимо гейтятся; перепланирование roadmap — норма.
- **Доверие к промптам** — каждое значимое правило существует как
  скрипт, проверка хеша или запрещённый exec; промпты несут только то,
  что гейты и так принуждают.
- **Самосертификацию** — ни один агент не помечает свою работу
  сделанной, не закрывает свою задачу и не аппрувит свой merge.

## Модель доверия (что где принуждается)

Три уровня принуждения — честно различённые:

- **Механический (вне досягаемости агента):** branch protection,
  обязательные ревью и статусы проверок живут на GitHub — пути записи
  у агента к ним нет. Конверты решений человека подписаны ключом,
  хранящимся вне воркспейса. Это жёсткие границы.
- **Механический, но с якорем в воркспейсе:** манифест целостности
  (`canon_manifest.json` с sha-картой, пины адаптер-хуков),
  scope-вайтлист и `project.json` проверяются на Gate 0 и на каждом
  коммите — но лежат в воркспейсе, где агент с exec может их
  переписать. Они надёжно **детектят** дрифт, но не могут
  **предотвратить** решительную правку изнутри. Зелёный результат
  читайте как «не изменено с последней проверки», а не «неизменяемо».
- **Конвенция:** обязательства уровня промпта (форматы отчётов,
  опрос, маркерная дисциплина). Они существуют, чтобы их аудировать,
  а не чтобы им верить — каждая значимая конвенция спарена с
  механической проверкой.

Физическая изоляция агентов (OOB/envelope-слой) — планируемое
укрепление для workspace-якорей, в этой поставке отсутствует.

## Роли одним взглядом

```
👨‍💻 DEV человек ──► гейты: roadmap, sign-off, manual_gate, эскалации
🧭 ROOT директор ──► план, черновики контрактов, спавн ролей, не коммитит
👷 CW исполнитель ──► код+тесты в белом списке, опрос до кода
🎨 DSG дизайнер ──► условный: закрывает делегированные оси контракта → impl spec
⚖️ JDG судья ──► вердикт только против замороженного контракта
🔍 RVW ревью-панель ──► доменные полы + вердикты-сигналы, PR-ревью только от агрегатора, ROOT не фильтрует
🤝 RES резолвер ──► ограниченные раунды спора → стоп/эскалация
🔀 GIT / 🏁 RA / 🧹 HYG ──► коммит кандидата → гигиена → merge-гейт → релиз
📖 RD читатель ──► аттестация файлов {path, sha256, ranges, anchor}
🛰️ PRT партнёры ──► консультации через шлюз, отдельное семейство моделей
```

## Жизненный цикл одного пункта

`план → 👨‍💻аппрув roadmap → issues → (опц. §2a пакетные контракты) →
контракт: draft→judged→👨‍💻sign-off(sha) → пред-консультация → спавн →
опрос до кода → код+тесты → раунды судьи ≤3 → ревью-панель → коммит GIT →
HYG → merge-гейт (изолированная копия + expected_sha + вердикты
ревьюеров + зелёные проверки; manual_gate-фрагмент → 👨‍💻) → релиз`

Пункт roadmap МОЖЕТ быть **эпиком**, декомпозированным на задачи:
эпик живёт на ветке `epic_issue_<N>-<slug>`, каждая задача проходит
полный цикл пункта на `issue_<M>-<slug>` и вливается в ветку эпика —
ревьюер-боты + проверки, без гейта человека, без подъёма версии
(issue задачи закрывается при попадании в эпик). Мерж
`эпик → default-ветка` проходит гейт `epic_merge` — каждая задача,
задекларированная в roadmap, должна быть влита (фрагмент) и
закрыта — поглощает накопленные фрагменты задач и ЯВЛЯЕТСЯ
границей релиза.

Лестница эскалации: вопрос → комитет уровня → архкомитет → человек
(терминал). Ограниченные петли доработок останавливают цикл вместо
треша.
