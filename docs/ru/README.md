# CCSDD — Committee Cycle Spec-Driven Development

Автономный пакет методики разработки для LLM-агентов под контролем
инженера-человека. Развёртывается в любой git-репозиторий и превращает
его в управляемый спеками процесс: архитектурный комитет проектирует,
исполнительный комитет строит, ревьюверы вне обоих комитетов
проверяют — а дисциплину держат не промпты, а механические гейты,
хеш-пиннутые артефакты и подписанные конверты решений человека.

Две оси версий, разделённые сознательно: **релиз продукта** `v0.2.13`
(тег этого репозитория) и **версия канона** `1.2.13`
(`MANIFEST.json.canon_version`, публикуется тегами `canon-v*` — ось,
которую проверяют deploy/release-ограждения). Продуктовые теги следят
за пакетом; canon-теги — за содержимым методики.

Требования: `git`, `python3`, `bash`. Конвейеру merge/release
(`repo_merge.sh`, `repo_release.sh`, `repo_pr_review.sh`, PR-проверки
`verify_constraints.sh`) дополнительно нужен аутентифицированный `gh`
на PATH — он источник правды о ревью, обязательных проверках и
привязке merge; `check_setup.sh` без него закрывается. Всё остальное
(commit-гейты, целостность канона, шлюз) без удалёнки работает.

## Что внутри методики

- **Спек-ориентированность (SDD)**: каждый пункт roadmap едет на
  контракте приёмки — сценарии Given/When/Then, белый список scope,
  risk-флаг; контракт замораживается по SHA-256 после sign-off.
- **Фазовый цикл (SDLC)**: план → контракт → имплементация → сборка →
  релиз — с явными условиями входа/выхода на каждой фазе, но по пункту,
  а не по продукту целиком.
- **Разделение полномочий (maker–checker)**: писатель не коммитит,
  коммитящий не мержит, мерж требует APPROVE каждого ожидаемого
  ревьюера на текущем head, ревьюверы вне комитетов.
- **Мультидоменная ревью-панель**: `canon/config/review_panel.json`
  объявляет ревьюеров по доменам (specs, security, quality, design,
  tester, fidelity, docs, product). У каждого домена — механический
  пол (аттестуется `gate_run.sh` в append-only журнал, привязан к
  SHA кандидата и хешу скрипта с base-ветки) плюс вердикт агента,
  публикуемый именованным сигналом `ccsdd/<domain>` через фордж-
  адаптеры (GitHub/GitLab/test). Формальный PR-review постит только
  агрегатор; merge-гейты проверяют все сигналы, все аттестации полов
  и финальный аппрув на точном head — отсутствие или устаревание
  означает блок, никогда не молчаливый пропуск.
- **GitOps-поставка самой методики**: деплой по MANIFEST.json с
  sha256-картой, релизные теги `canon-v*`, детект дрифта по хешам.
- **Аттестации вместо доверия**: конверты решений человека с подписью
  и привязкой к хешу артефакта, журналы вердиктов, per-repo канарейка
  целостности правил.
- **Релизные фрагменты (changesets)**: каждый PR несёт
  `.changes/<slug>.md` (`bump`, `user_visible`, `issue`); версия на
  Release-on-Merge вычисляется из фрагментов, а `manual_gate: true`
  паркует merge до явного решения человека.

## Чем отличается

- Дисциплина — код, а не конвенция: каждое значимое правило
  существует как скрипт-гейт или проверка хеша; промпты несут только
  то, что гейты и так принуждают.
- Человек — верх эскалации и держатель гейтов (`👨‍💻`), а не наблюдатель.
- Vendor-нейтральность: ядро (`canon/`) не знает ни о каком рантайме;
  клей под конкретного агента генерируют адаптеры.

## Укладка

```
canon/
  MANIFEST.json        # files + sha256 + gitignore-политика; единственный авторитет
  root/canon/          # зеркало того, что попадёт в проект как canon/
    RULES.md           # ядро правил инстанса; канарейка целостности в хвосте
    agents/            # профили ролей (code_writer, judge, reviewer, git, ...)
    bin/               # гейт-скрипты (check_setup, verify_*, repo_*, ship_*)
                       # + тест-сюиты: gate_tests.sh, pipeline_tests.sh
    specs/             # harness.md (цикл), quota, gateway, canon_gate,
                       # glossary, fleet*
    config/policy.json # нейтральная модель разрешений (deny/allow)
    templates/         # roadmap.template.md (нормативная форма пункта)
adapters/
  devin.sh             # клей для рантайма Devin
  generic.sh           # указатель AGENTS.md (baseline для любого рантайма)
tools/
  start_project.sh     # деплой канона + вызов адаптеров (всё по аргументам)
  manual_start_project.sh  # интерактивный опросник -> start_project.sh
README.md              # корень репо: двуязычный индекс документации
docs/
  ru/                  # этот файл, методика, схемы
  en/                  # тот же набор на английском
```

`*` `specs/fleet.md` — спецификация оркестраторного слоя; в этой поставке
не реализуется, включена как референс (на неё ссылаются другие спеки).

## Быстрый старт

```bash
tools/manual_start_project.sh
```

Опросит: директория проекта (предложит `git init`, remote, repo-slug),
язык, источник канона, **целевые рантаймы** (поддерживается несколько
клеев сразу, напр. `devin,generic`), protected-пути. Покажет итоговую
команду и после подтверждения выполнит `start_project.sh`.

Тот же вызов напрямую (его позже сможет делать оркестратор):

```bash
tools/start_project.sh --workspace /path/to/repo \
    --adapter devin --adapter generic --text-lang ru
```

После деплоя откройте инстанс агента с `working_directory` = корень
проекта. Первое действие инстанса — прочитать `canon/RULES.md` (последняя
строка `CANARY_EOF_TOKEN:<token>`, иначе halt) и прогнать
`canon/bin/check_setup.sh`.

## Что делает деплой

1. Фенсинг релиза: тег `canon-v<version>` в репозитории канона
   (`--allow-untagged-canon` — логируемый дрифт).
2. Verbatim-деплой всех файлов манифеста с проверкой sha256;
   устаревшие файлы прошлого канона удаляются.
3. Per-repo канарейка `cnr-<hex>` → хвост `canon/RULES.md` +
   `canon/canon_manifest.json` (штамп с sha-контролем дрифта).
4. Блок `# >>> canon` в `.gitignore`; антрек задеплоенных путей
   инфра-коммитом только на дефолтной ветке.
5. `canon/project.json` при отсутствии.
6. `canon/bin/check_setup.sh` — fail-closed.
7. Адаптеры: рантайм-клей поверх нейтрального `canon/`.

## Адаптеры

- **devin** — создаёт точку входа для рантайма Devin: `.devin/` со
  ссылками на `canon/*`, `config.json` с правами, скомпилированными из
  `policy.json`, `.windsurfrules` → `canon/RULES.md`.
- **generic** — помеченный блок в `AGENTS.md`: «читай canon/RULES.md».
  Слоя принуждения нет — дисциплину держат гейты на коммитах.
- Адаптеры не конкурируют: одному проекту можно выдать несколько клеев.
  Свой адаптер — скрипт `adapters/<name>.sh`, принимающий `<workspace>`.
- Профили агентов декларируют вендор-нейтральный тир модели
  (`model: tier:heavy|tier:medium`); `adapters/model_map.json`
  сопоставляет тир с id модели конкретного рантайма — в каноне нет
  вендорных имён.

## Гейты человека (ваша роль в цикле)

- `👨‍💻` аппрув roadmap; sign-off контракта каждого пункта (sha в конверт;
  опционально — пакетная проработка первых N контрактов, `harness.md`
  §2a); решения по эскалациям и PLAN_DELTA. Merge объективен:
  доменные APPROVE-сигналы + зелёные проверки + `expected_sha`; явный
  стоп человека — через `manual_gate: true` в `.changes`-фрагменте.
- Sign-off человека — SSH-подпись через `canon/bin/human_sign.sh`:
  `init` регистрирует существующий публичный ключ в `allowed_signers`
  (приватный ключ в воркспейс не попадает), `sign --verdict approve
  --artifact <sha> --out -` печатает компактную строку
  `CCSDD-SIGNOFF-1|...`, которую можно вставить в чат агенту или
  сохранить в `canon/human_signoffs/`; `verify` проверяет подпись,
  привязку к артефакту, свежесть 7 дней и replay nonce — всё офлайн.
  Удалённый человек подписывает на ноутбуке и вставляет строку;
  `consume` сжигает nonce только после завершения мержа.
- `canon/bin/setup_repo.sh` применяет контрольную плоскость репо:
  защита ветки (с сохранением существующих required checks), укладка
  `.changes`-фрагментов и печать ожидаемого разделения
  `review.gh_bin`/`merge.gh_bin` с правами токена ревьюера.
- Публикация новой версии канона — только через `canon/bin/canon_pub.sh`,
  по тому же SSH-подписанному конверту через `human_sign.sh`.

## Тесты

Два самодостаточных сьюита негативных тестов (scratch-репозитории,
без сети):

```bash
canon/root/canon/bin/gate_tests.sh      # commit-обёртки и гейты
canon/root/canon/bin/pipeline_tests.sh  # интегрити деплоя, шлюз,
                                        # привязка ревьюеров в
                                        # repo_merge, release-
                                        # provenance, roll-forward
                                        # миграций
```

## Не реализовано в этой поставке

Оркестраторный слой (`fleet.md`: шина, mailbox, lease/epoch, OOB,
fleet_registry, bridge-хуки). Спеки оставлены для контекста; завязанные
на шину механики в standalone-режиме просто не вызываются.
