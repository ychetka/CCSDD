# CCSDD — Committee Cycle Spec-Driven Development

An autonomous package of a spec-driven development methodology for
LLM agents supervised by a human engineer. Deploy it into any git
repository and it becomes a spec-governed process: an architecture
committee designs, an executive committee builds, reviewers outside
both committees verify — and discipline is held not by prompts but by
mechanical gates, hash-pinned artifacts, and signed human decision
envelopes.

Two version axes, deliberately separate: **product release** `v0.2.12`
(the repo tag on this package) and **canon version** `1.2.12`
(`MANIFEST.json.canon_version`, released as `canon-v*` tags — the axis
deploy/release fencing cares about). Product tags track the package;
canon tags track the methodology payload.

Requirements: `git`, `python3`, `bash`. The merge/release pipeline
(`repo_merge.sh`, `repo_release.sh`, `repo_pr_review.sh`,
`verify_constraints.sh` PR checks) additionally needs an authenticated
`gh` on PATH — it is the remote truth source for reviews, required
checks and merge binding; `check_setup.sh` fails closed without it.
Everything else (commit gates, canon integrity, gateway) is remote-free.

## What the methodology is built on

- **Spec-driven development (SDD)**: every roadmap item rides on an
  acceptance contract — Given/When/Then scenarios, scope whitelist,
  risk flag; the contract is frozen by SHA-256 after sign-off.
- **Phased cycle (SDLC)**: plan → contract → implementation →
  assembly → release, with explicit entry/exit conditions per phase —
  but per item, not for the whole product at once.
- **Separation of duties (maker–checker)**: the writer cannot commit,
  the committer cannot merge, merges require every expected reviewer's
  APPROVE on the current head, reviewers sit outside both committees.
- **Multi-domain review panel**: `canon/config/review_panel.json`
  declares per-domain reviewers (specs, security, quality, design,
  tester, fidelity, docs, product). Each domain pairs a mechanical
  floor (attested by `gate_run.sh` into an append-only journal, bound
  to the candidate SHA and the base-branch script hash) with an
  agent verdict published as a named `ccsdd/<domain>` signal through
  forge adapters (GitHub/GitLab/test). Only the aggregator may post
  the formal PR review; merge gates verify every signal, every floor
  attestation, and the final approval on the exact head — missing or
  stale means blocked, never silent pass.
- **GitOps delivery of the methodology itself**: MANIFEST.json +
  sha256 deploy, `canon-v*` release tags, drift detection by hash.
- **Attestation instead of trust**: signed human decision envelopes
  bound to artifact hashes, verdict journals, a per-repo canary for
  rules integrity.
- **Release fragments (changesets)**: every PR carries a
  `.changes/<slug>.md` fragment (`bump`, `user_visible`, `issue`);
  the Release-on-Merge version is computed from fragments, and
  `manual_gate: true` parks the merge pending an explicit human
  decision.

## How it differs

- Discipline is code, not convention: every rule that matters exists
  as a gate script or a hash check; prompts carry only what gates
  already enforce.
- The human is the top of the escalation ladder and the gate holder
  (`👨‍💻`), not an observer.
- Vendor neutrality: the `canon/` core knows nothing about any
  runtime; per-agent glue is generated by adapters.

## Layout

```
canon/
  MANIFEST.json        # files + sha256 + gitignore policy; sole authority
  root/canon/          # mirrors what lands in a project as canon/
    RULES.md           # instance kernel rules; integrity canary at the tail
    agents/            # role profiles (code_writer, judge, reviewer, git, ...)
    bin/               # gate scripts (check_setup, verify_*, repo_*, ship_*)
                       # + test suites: gate_tests.sh, pipeline_tests.sh
    specs/             # harness.md (the cycle), quota, gateway, canon_gate,
                       # glossary, fleet*
    config/policy.json # neutral permission model (deny/allow)
    templates/         # roadmap.template.md (normative item shape)
adapters/
  devin.sh             # glue for the Devin runtime
  generic.sh           # AGENTS.md pointer (baseline for any runtime)
tools/
  start_project.sh     # canon deploy + adapter invocation (all CLI args)
  manual_start_project.sh  # interactive wizard -> start_project.sh
README.md              # repo root: bilingual documentation index
docs/
  en/                  # this file, methodology, diagrams
  ru/                  # the same set in Russian
```

`*` `specs/fleet.md` — the orchestration-layer spec; not implemented in
this distribution, included as reference (other specs link to it).

## Quick start

```bash
tools/manual_start_project.sh
```

The wizard asks for: project directory (offers `git init`, remote,
repo slug), language, canon source, **target runtimes** (multiple glue
allowed, e.g. `devin,generic`), protected paths. It shows the exact
command and runs `start_project.sh` on confirmation.

The same call directly (what a future orchestrator will use):

```bash
tools/start_project.sh --workspace /path/to/repo \
    --adapter devin --adapter generic --text-lang ru
```

After deploy, open an agent instance with `working_directory` = project
root. Its first move is to read `canon/RULES.md` (last line must be
`CANARY_EOF_TOKEN:<token>`, otherwise halt) and re-run
`canon/bin/check_setup.sh`.

## What the deploy does

1. Release fencing: `canon-v<version>` tag must exist in the canon
   repo (`--allow-untagged-canon` = logged drift).
2. Verbatim deploy of every manifest file, sha256-verified; stale
   files from an earlier canon are removed.
3. Per-repo canary `cnr-<hex>` -> tail of `canon/RULES.md` +
   `canon/canon_manifest.json` stamp (drift integrity).
4. `# >>> canon` block in `.gitignore`; untracking of deployed paths
   via an infra commit on the default branch only.
5. `canon/project.json` generated if absent.
6. `canon/bin/check_setup.sh` — fail closed.
7. Adapters: runtime glue on top of the neutral `canon/`.

## Adapters

- **devin** — creates the Devin runtime entry point: `.devin/` with
  links onto `canon/*`, a `config.json` with permissions compiled from
  `policy.json`, `.windsurfrules` -> `canon/RULES.md`.
- **generic** — a marked block in `AGENTS.md`: "read `canon/RULES.md`".
  No enforcement layer — discipline is held by commit gates.
- Adapters do not compete: one project may carry several glues.
  Your own adapter = a script `adapters/<name>.sh` taking `<workspace>`.
- Agent profiles declare a vendor-neutral model tier
  (`model: tier:heavy|tier:medium`); `adapters/model_map.json` maps
  each tier to a runtime-specific model id, so the canon carries no
  vendor names.

## Human gates (your role in the cycle)

- `👨‍💻` roadmap approval; per-item contract sign-off (sha-bound
  envelope; optional batch elaboration of the first N contracts,
  `harness.md` §2a); escalation and PLAN_DELTA decisions. The merge
  itself is objective — domain APPROVE signals + green checks +
  `expected_sha`; an explicit human stop is opt-in via
  `manual_gate: true` in a `.changes` fragment.
- Human sign-offs are SSH signatures issued by
  `canon/bin/human_sign.sh`: `init` registers your existing public
  key in `allowed_signers` (no private key ever enters the
  workspace), `sign --verdict approve --artifact <sha> --out -`
  prints a compact `CCSDD-SIGNOFF-1|...` line you can paste into the
  agent chat or save under `canon/human_signoffs/`; `verify` checks
  signature, artifact binding, 7-day freshness and nonce replay —
  all offline. Remote humans can sign on their laptop and paste the
  line; `consume` burns the nonce only after the merge lands.
- `canon/bin/setup_repo.sh` applies the repo-side control plane:
  branch protection (preserving existing required checks), the
  `.changes` fragment layout, and prints the expected
  `review.gh_bin`/`merge.gh_bin` split plus the token scopes the
  reviewer identity needs.
- Canon releases go only through `canon/bin/canon_pub.sh`, gated by
  the same SSH-signature envelope verified via `human_sign.sh`.

## Tests

Two self-contained negative-test suites (scratch repos, no network):

```bash
canon/root/canon/bin/gate_tests.sh      # commit-wrapper gates
canon/root/canon/bin/pipeline_tests.sh  # deploy integrity, gateway,
                                        # repo_merge binding, release
                                        # provenance, migration rollout
```

## Not implemented in this distribution

The orchestration layer (`fleet.md`: bus, mailbox, lease/epoch, OOB,
fleet_registry, bridge hooks). The spec is kept for context; bus-bound
mechanics are simply not invoked in standalone mode.
